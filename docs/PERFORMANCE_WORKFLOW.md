# Performance workflow and resume guide

Read [the current results](PERFORMANCE.md) first. Optimization is paused pending
New Nintendo 3DS/2DS access. This guide preserves the process and commands used
for the accuracy-preserving performance work; temporary artifact directories
are evidence caches, not prerequisites for resuming.

## Start from a known state

1. Read `AGENTS.md`, `README.md`, the affected core modules and their tests.
   The core lives in `crates/vibe-emu-core/src/`; frontend code stays separate.
2. Inspect `git status`, fetch origin, and compare the working branch with
   `origin/main`. Preserve unrelated edits. Record the full baseline and
   candidate commit IDs and any uncommitted diff. Use a `codex/` branch for
   new work, or continue an explicitly assigned branch.
3. Run the existing accuracy tests before diagnosing a performance regression.
   ROM bundles download on the first integration test run; preserve them.
   Boot fixtures prefer the original host with an immutable mirror as backup,
   and verify the original published
   SHA-256 hashes; cached bytes are checked too. If a download host fails,
   confirm the source and byte identity before changing URLs. Exercise the
   affected tests from a backed-up empty fixture cache; a warm local cache
   can conceal CI download failures. Never substitute different boot code.
   See [BUILD.md](../BUILD.md) for Linux dependencies and other host setup.
4. Pick one measured bottleneck. Make an isolated experiment, compare it with
   the same baseline, and retain it only after checking accuracy and the full
   workload mix. Keep rejected variants out of the final source.

Do not infer that a process stopped because a polling request timed out. Poll
its existing handle or inspect its authoritative status/log; restart only if
it actually ended. Keep builds/tests out of wall-clock benchmark sessions.

## Build comparable binaries

Use Python 3.12+ and the same Rust compiler for both builds. Commands below
run from the repository root. Replace `BASELINE_COMMIT` with the recorded
commit; omit `--revision` to snapshot the current working tree.

```bash
python3 scripts/build_profile_revision.py --revision BASELINE_COMMIT \
  --output target/perf/baseline
python3 scripts/build_profile_revision.py --output target/perf/candidate
```

Each command prints an absolute binary path in a unique `run-*` directory.
The builder uses a minimal Cargo workspace, source-pinned dependency versions,
optimization level 3, thin LTO and one codegen unit. It uses the **current
checkout's same harness for both revisions**, adapting old CPU APIs to
single stepping if necessary. `--offline` is available once dependencies are
cached. `--prepare-only` creates the snapshot without compiling it.

Preserve `revision.txt`, `source-files.sha256`, `compiler.txt`, `cargo.txt`,
`build-environment.json`, `build-command.json`, `cargo-metadata.json`, source
snapshots, resolved lockfiles, build logs and binaries. Verify source equality
with the revisions being claimed, compare compiler/environment/lockfile
identity, and hash ROMs/binaries. Unexpected dependency resolution is an error.
Native-CPU flags, PGO and other compiler overrides need separate comparisons.
If replacing snapshot files manually, update their timestamps so Cargo cannot
reuse stale objects. Prefer a new snapshot over hand-editing one.

## Fixed benchmark corpus

```bash
python3 scripts/benchmark_suite.py /absolute/baseline/profile_core \
  /absolute/candidate/profile_core \
  --polished-rom /path/to/polishedcrystal-debug-3.2.3.gbc \
  --output target/perf/comparison --runs 7 --counters
```

The output directory must be new. The script validates inputs, generates the
synthetic ROM, runs every case serially, and saves raw logs and SHA-256 hashes.
`--counters` requires Linux `perf` access; omit it on other hosts or when
hardware counters are unavailable. Do not silently replace unavailable
counters with zero. Use `benchmark_core.py` directly for an individual ROM.

| Case | ROM beneath `crates/vibe-emu-core/test_roms/` | Measured / warmup |
| --- | --- | ---: |
| polished | User-supplied Polished Crystal 3.2.3 | 1800 / 300 |
| silent | Same ROM, audio output disabled | 1800 / 300 |
| dmg | `dmg-acid2/dmg-acid2.gb` | 600 / 120 |
| cpu | `blargg/cpu_instrs/cpu_instrs.gb` | 600 / 120 |
| cgb | `cgb-acid2/cgb-acid2.gbc` | 600 / 120 |
| wave | `blargg/cgb_sound/rom_singles/12-wave.gb` | 600 / 120 |
| hell | `cgb-acid-hell/cgb-acid-hell.gbc` | 600 / 120 |
| window | Generated by `scripts/generate_window_benchmark.py` | 600 / 120 |

The Polished ROM used here has SHA-256
`a8dc269c102152be2bd5eb42cf0f5d13fd8d10dadf6fadd88df802caf26e9c42`.
Supply your own copy; it is not distributed with this benchmark tooling.

The shared harness loads bytes without battery saves or wall-clock RTC,
selects DMG/CGB from the header, advances fixed 70,224-dot budgets and carries
instruction overshoot forward. It generates/drains 48 kHz stereo unless
explicitly silent. Timed regions exclude hashing/draining and warmup.
Comparisons alternate AB/BA order and reject any difference in model, frame
budget, dot count, video hash, audio hash, sample count or final PC.

Report medians, not best runs. The original-corpus aggregate is the geometric
mean of seven baseline/candidate median ratios; **exclude synthetic window**.
Keep regressions visible. Measure a whole-branch comparison directly; never
multiply speedups from separately timed passes. Linux results do not prove
Windows performance, and an intro/test-ROM corpus is not general gameplay.

## Repeatable indoor gameplay

The previously temporary harness is now
[`profile_polished_room.rs`](../crates/vibe-emu-core/examples/profile_polished_room.rs).
Build both revisions with the same workload option:

```bash
python3 scripts/build_profile_revision.py --revision BASELINE_COMMIT \
  --workload polished-room --output target/perf/room-baseline
python3 scripts/build_profile_revision.py --workload polished-room \
  --output target/perf/room-candidate
python3 scripts/benchmark_core.py /absolute/room-baseline/profile_core \
  /absolute/room-candidate/profile_core /path/to/polishedcrystal-debug-3.2.3.gbc \
  --frames 3600 --warmup 6600 --runs 7
```

The printed binaries retain the name `profile_core` even for this workload.
The zero-based frame input sequence is:

- Before frame 3000: Start for two frames every 120 frames.
- Frames 3000–5999: Start for two frames every 600 frames; otherwise A for
  two frames every 30 frames.
- Frames 6000–6005: Start to close the menu; neutral until frame 6120.
- From frame 6120: right, down, left, up, each held for 90 frames, repeating.

This sequence was screenshot-verified to move around one indoor room. It is
ROM-specific; after changing the ROM or setup, verify that it still reaches
movement rather than timing a menu. Set `VIBE_PERF_SCREENSHOTS` to an existing
directory to write PPM frames every 1200 frames during a verification run.
**Unset it for timing.** Screenshot I/O is not a performance workload.

For gameplay instruction estimates, count a 3600-frame run and a 1-frame run,
both with 6600 warmup frames, then subtract. This cancels most setup cost;
divide the difference by `3599 * 70224 / 4194304` emulated seconds. Compare
both long-run and prefix signatures across revisions. This still includes
hashing/draining and is not an exact core-only counter measurement.

## Profile, change, and prove equivalence

On Linux, a typical sample run is:

```bash
perf record -e cycles:u -F 999 -o target/perf/cycles.data -- \
  /absolute/candidate/profile_core /path/to/rom.gbc 12000 300 audio
perf report --stdio -i target/perf/cycles.data
perf stat -e instructions:u,cycles:u -x, -o target/perf/counters.csv -- \
  /absolute/candidate/profile_core /path/to/rom.gbc 600 120 audio
```

Inspect lost samples and separate exclusive from inclusive costs. Normal
counter runs cover the entire process, including startup/warmup/hash/drain;
720 fixed frames represent `720 * 70224 / 4194304` emulated seconds. Do not
compare them as if they covered only the timed region.

The successful approach has been to remove redundant work between observable
hardware events, while preserving the original path as an independent test
reference. Important locations and constraints:

- `cpu.rs`: `run_for_dots`, bus synchronization and clock boundaries. Flush
  before observable accesses; stop at interrupt, DMA, serial and frame limits.
  Keep multi-M-cycle APU call ordering, STOP/HALT, speed-switch and IE-stack
  interrupt quirks. The scalar `step` runner remains a scheduling reference.
- `mmu.rs` and `timer.rs`: peripheral queues, logical DIV and deadline renewal.
  Never recompute a PPU deadline with queued dots. Do not skip timer reload,
  pending writes, RTC observations, bus latches, watchpoints or DMA ownership.
- `ppu.rs`: independent original dot path, fetch timestamps, FIFO state,
  raster/window tile transactions and OBJ-size captures. Compare timing state,
  not just a final screenshot; retain DMG/CGB revision/tuning coverage.
- `apu.rs`: compare every stereo sample and exact floating-point behavior.
  Settled filters may skip arithmetic only at an exact fixed point. No sample
  dropping, approximate recurrence, lower sample rate or forced-zero shortcut.
- Save states: transient scheduling/cache fields must be safely flushed or
  reconstructed. Compare save/restore continuation, including DMA and audio.

Useful focused tests include `clock_batch`, `peripheral_batch`, `halt_batch`
and `state_buffers`, plus the PPU/APU/timer unit references. Expand the nearest
reference test for new boundaries, rather than copying the optimized logic
into an expected-value implementation. Reject unexplained signature changes.

## Required final validation

```bash
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test
cargo test --release
cargo check -p vibe-emu-core --all-features
cargo test -p vibe-emu-core --no-default-features --lib --test state_buffers
git diff --check
```

Loopback-network tests need permission to bind local sockets. Investigate
third-party ROM failures; never remove or ignore them to retain an optimization.
`cargo gambatte_test` is separate and opt-in. Keep its known failures distinct
from default-suite regressions. `TEST_STATUS.md` is a generated compatibility
report, not proof that a new optimization passed. Record commands, exit status,
counts and ignored tests from actual logs; the nested tuning subprocess has
its own summary and must not be accidentally omitted or double-counted.

Then compare the final measured source against the final tested source, update
[PERFORMANCE.md](PERFORMANCE.md), and commit a focused change. A PR should name
baselines, gains/regressions, accuracy evidence and remaining hardware limits.
Check CI on the exact PR head before merging. For dependency advisory failures,
apply patched versions, rerun the full checks and regenerate notices with the
CI-pinned cargo-about version (see BUILD.md); keep advisory checking enabled.
Verify that benchmark dependency pins still describe the final core; keep optimization paused if
hardware availability or the user's requested stopping point has not changed.

## Resume on New Nintendo 3DS/2DS

Start with the hardware checklist in [PERFORMANCE.md](PERFORMANCE.md#hardware-validation).
The host gate is already met for the limited corpus; further host-only
optimization is not the next acceptance test. Rebuild and measure on the target.
Use buffer save-state APIs and `--no-default-features` if filesystem-backed
`state-store`/`tempfile` prevents target compilation. A library build does not
prove that an executable links or runs. Revisit the expanded decoder's cache
cost before assuming desktop inlining gains transfer to ARM11.
